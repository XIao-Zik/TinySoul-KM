# i18n — client-local presentation localization

## Positioning

UI text is localized entirely on the client. The backend stays
language-neutral: it serves data and English protocol text, and the frontend
renders presentation strings in the user's chosen locale. Localization never
translates backend content — message bodies, document text, identifiers,
enum/state values and refs render as delivered.

## gettext-style keys

The English source string IS the translation key:

- Locale `en` renders the source itself — there is no English dictionary.
- Locale `zh-CN` looks up a Chinese overlay dictionary; untranslated strings
  degrade to English, never to a raw key.
- Sources are collapsed to single spaces before lookup, so JSX multi-line
  strings resolve regardless of source formatting.

This matches the existing Settings mechanism (`features/settings/i18n/`):
backend-declared catalog fields are English sources with a `zh-CN` overlay,
now gated by the same global locale instead of always applying Chinese.

## Ownership

- `src/i18n/locale.ts` — pure `Locale` type, default (`zh-CN`) and options.
- `src/i18n/index.ts` — merges the per-feature dictionary segments, exports
  `translate`, non-reactive `t` (module/plain-function contexts) and the
  reactive `useT()` hook (components). No other files import dictionaries.
- `src/i18n/dicts/zh-CN-<feature>.ts` — one segment per feature (shell, chat,
  context, trace, history, resources, workspace, home, memory, runtime,
  settings). Each segment is owned by its feature so parallel edits never
  conflict.
- `src/features/settings/i18n/index.ts` — the settings surface keeps its
  field-path catalog overlay; `settingsText`/`localizeField`/
  `localizeDocument` follow the global locale.

Components call `useT()`; module constants keep English sources and are
wrapped at the render site. Every view's top-level component subscribes via
`useT()` so a locale switch re-renders the subtree; the settings root remounts
on locale change for the same reason.

## Locale state

`locale` lives in `appStore` next to `theme` (client-local preference,
persisted in `tinysoul-ui-state`, default `zh-CN`). The switcher is on
Settings → Interface → Language and applies immediately.

## Testing

`test/setup.ts` pins every test to the `en` locale: assertions verify the
English source (the key itself), keeping them stable while dictionaries grow.
zh-CN rendering has dedicated coverage in `src/i18n/index.test.ts`; the
settings localization test opts into `zh-CN` explicitly.

The suite runs with `fileParallelism: false`: the real-timer poll tests
(e.g. jobsTab) starve when many workers compete with this machine's dev
backend/frontend processes, and no worker cap or timeout bound removed the
flake. Sequential files are deterministic; focused single-file runs stay fast.
